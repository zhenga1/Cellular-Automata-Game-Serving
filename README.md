# Cellular Automata Sandbox

A 3D falling-sand sandbox that runs in the browser: pour sand, water, lava and fire and watch them interact.

**Play it:** https://zhenga1.github.io/Cellular-Automata-Game-Serving/ (needs a browser with WebGL 2). The sandbox is at `sim.html` and the challenge levels are at `play.html`.

The original C++/OpenGL project (CS184 final project) is compiled to WebAssembly with Emscripten. This repo only holds the built files that GitHub Pages serves.

## Controls

| Input | Action |
| --- | --- |
| Left-drag | Look around |
| Right-drag | Pan |
| `W` `A` `S` `D` / arrow keys | Move |
| `Space` / `Shift` | Up / down |
| Scroll | Move the red cursor box nearer / farther |
| `F` | Place the selected material at the cursor box |
| `1`–`0`, `T`, `X` | Pick a material / turf / delete |
| `B` | Open / close the rulebook (how each material behaves) |
| `[` `]` | Brush size |
| `P` | Pause / resume |
| `C` | Show / hide the cursor box |
| `L` | Toggle gravity |
| `H` | Hide the control panel |

The panel also has a world picker, spawners (blocks that keep emitting a material), reset, and saving/loading world files (`.demo` or `.demo.gz`).

## Play mode

`play.html` is the challenge mode (`play.html?level=<id>` opens a specific level). The first
game is **Save the Villagers**:

- **Level 1, Lava Fork** (`lava-fork`): lava pours from a vent down a gutter that forks halfway.
  One fork runs through a stone archway into the village, the other through a gap in the wall
  into an empty pit. You get exactly one 3x3x3 block of stone. Blocking the archway makes the
  lava back up and spill into the pit; you win by holding out for 900 simulation ticks with the
  village intact. Doing nothing, blocking the wrong opening, or blocking the gutter itself all
  lose (each case was tested in the real sim).
- **Level 2, Wildfire** (`wildfire`): a wildfire is burning across a dry meadow toward four
  wooden villagers. The kit is stone, sand, water, snow and delete, with spawners and 20
  placements. You win when the fire has burned out with all four villagers intact.

The second game is **Destroy the World**:

- **Level 1, Ember Isle** (`ember-isle`): five islands of sand and grass, separated by stone gullies
  that fire cannot cross, with wooden plank fuses linking them into two chains. You have two fires;
  burn at least 97% of the world. One fire in each chain wins (about 98% burns); two in the same
  chain leave the other chain standing (about 39% burns). Both were tested in the real sim.

A third game, **Build a Path**, has one **draft** level:

- **Aqueduct** (`aqueduct`): a spring on one plateau, the village's empty pool on the other, and an
  old aqueduct across the chasm between them whose deck is missing. Lay the deck with stone (3
  placements, 2 needed) so 300 blocks of water reach the pool. Without a deck all the water falls
  into the chasm and is lost; with it the pool filled in about 15 seconds in testing.

Each level starts paused so you can build first. Play mode reads the world back by calling the
sim's save function and parsing the result a couple of times a second, since the WebAssembly
build exposes no way to read cells directly.

## Worlds

Open a specific world with `sim.html?world=<id>`: `classic` (Sand Hill), `cave` (Dark Cave), `beach` (Beach), `city` (Concrete Jungle) or `park` (Park). The home page lists them too.

## Rebuilding

In the source repo (`cs184-final-proj`, branch `aaron_web_edit`), in a terminal where `emsdk_env` has been run:

```powershell
./build_web.ps1 -Deploy C:\path\to\this\repo
```

Then commit and push this repo. The build tags every file URL with a hash of the build, so browsers never combine files from two different builds.

To add a world: put its `.demo.gz` and a thumbnail in the source repo's `worlds/` folder, add an entry to `worlds/worlds.json`, and rebuild. The generated worlds come from `worlds/generate_worlds.py`.

**Careful:** the build overwrites `index.html`, so the link to Play mode has to go into the
source repo's `web/home.html` as well, or the next deploy will drop it. `play.html` and
`levels/` are not touched by the build.

## Rebuilding the levels

Levels live only in this repo. Edit `levels/make_levels.py` and run it:

```powershell
cd levels
python make_levels.py
```

That rewrites every `<id>.demo.gz`, `<id>.png` and `levels.json`, including a content hash that
`play.html` uses for cache busting, so a rebuilt level is picked up straight away.

Fire needs a lot of fuel touching it to keep going: every burnable block next to a flame has
only a 1-in-7 chance of catching and otherwise turns to smoke. A single sheet of grass or a
one-plank bridge burns out instead of spreading, which is why the meadow is four blocks of
grass deep and the footbridge is a solid span. `MEADOW_TOP` and `LAWN_TOP` are the knobs for
that if a level needs retuning.
